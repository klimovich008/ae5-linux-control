## The strongest saved measurement

An electrical loopback — AE-5 headphone jack into the motherboard's `L-In`,
captured on card 2, an independent card with its own clock — playing a 1 kHz
sine at −18 dBFS with `Enable OutFX` **off**:

| Instrument | THD | 2f | 4f | 5f |
|---|---:|---:|---:|---:|
| Internal What U Hear tap (digital) | **25.96%** | −14.1 dB | −17.1 dB | −20.6 dB |
| Line-In loopback (analog output) | **26.96%** | −13.7 dB | −17.0 dB | −19.9 dB |

Signal-to-noise 142 dB on the tap, 65 dB on the loopback, no clipping on
either. The harmonics agree within about 1 dB at every order.

The source fixture itself was rechecked at 0.00074% THD. Its SHA-256 is
`4567413a4ba9e9b9a739f630aa7c5fa25426e13ebacb5efe64d8117a201dc9f9`.
The three private WAVs have been preserved outside Git under
`~/.cache/ae5-control/session-20260727-thd/`.

The safe conclusion is narrower than the one originally recorded:
**the dominant distortion is present at the internal digital tap and is then
reproduced at the analog output**. The analog stage may add a small residual,
but it is not the primary source of this harmonic pattern. The cable and
motherboard input are also not independently calibrated, so this is excellent
fault isolation rather than a final analog-performance benchmark.

`Enable OutFX` off is **not a CA0132 processor bypass**. In the Linux driver it
qualifies every individual output effect off, re-runs normal output selection,
and leaves the CA0132 DSP/router/mixer path active. Only the project's AE-5
Direct Mode bypasses that path. The measurement therefore shows distortion in
the normal digital route with the effect blocks disabled; it does not show a
"bypassed processor" modifying samples.

The next discriminating comparison is normal route with OutFX off versus true
Direct Mode, captured electrically at the line input. An OutFX on/off pair is
still useful for isolating the effect blocks, but cannot establish DSP bypass.

## Corrections

Things stated during the session that later evidence contradicted. They are
listed because the reasoning that produced them looked sound at the time.

**"The buzz is an analog-stage fault invisible to the digital tap."** Based
on microphone captures showing impulsive bursts absent from the tap. The
loopback shows tap and analog output agreeing within 1 dB. The microphone
work was too noisy and too dependent on headphone placement to support the
claim. Withdrawn.

**"Non-snoop DMA is the likely mechanism."** The card does run in non-snoop
mode, which is real and worth knowing. But that corrupts the buffer after
the DSP, so the tap would be clean — and it is not. Weakened, not
eliminated: corruption upstream of the mix point would still appear.
`snoop=1` is staged in `/etc/modprobe.d/ae5-snoop.conf` and applies on the
next boot, so the test is cheap to finish.

**"Headphone gain range was the cause."** The SHP9500 are 32 Ω and sit one
ohm outside the `Low (16-31 Ω)` band that had been forced all night; the
system kept restoring `Medium` and was right to. Switching to `Low` was
quieter but not distorted, so the range is not the fault. The gain is now
`Medium`, which is correct regardless.

**"X-Bass and Surround caused it."** They differed between a faulty and a
clean capture, but `Enable OutFX` was off in both. Maks disproved it
directly by re-enabling them with no audible change.

**A control-diff parser bug** briefly reported the wrong five controls: it
matched the `; type=...,values=1` metadata line rather than the `: values=`
line. Fixed before any conclusion rested on it.

**"`Enable OutFX` off bypasses the processor."** The upstream driver source
contradicts this. `ca0132_pe_switch_set()` disables the individual effects
through `ca0132_effects_set()` and calls `ca0132_alt_select_out()`, which still
programs the normal DSP output router, tuning mute, channel mode, speaker EQ
selection and bass-redirection state. Withdrawn. Direct Mode is the project's
separate, real DSP-bypass path.

## Confirmed findings

**The headphone jack was ranked as speakers.** ACP builds one port per
`Output Select` value, and upstream `analog-output.conf.common` scores the
Speakers option 10 against Headphone 9. On this card that put the headphone
jack driven as Speakers (priority 9910) above the same jack driven as
headphones (9909), with the wrong one reporting availability "unknown" so
nothing ruled it out. This is the fault the project started from — headphones
silent until Line Out was selected and the routing corrected by hand in
alsamixer. Inverting those priorities on the AE-5 path (`5dea6fc`) fixed
automatic selection but did not remove the impossible port: WirePlumber could
restore a previously saved
`sound-blaster-ae5-output-headphones;output-speaker` choice on a later boot.
The current worktree replaces the generic include with one exact, required
`Headphone` option. Static ACP and transactional rootless-install validation
pass. The later live exact-route and guarded transition result is recorded
near the end of this document.

**The DSP oscillation is not caused by the patch queue.** Measured on the
stock Nobara kernel, idle, all PCMs closed: `Enable OutFX` on −3.60 dB, off
−36.31 dB, on −5.05 dB. The patched kernel read −2.80 / −38.33 / −2.80. The
behaviour is identical, so this is upstream `snd_hda_codec_ca0132` or the
silicon (`905ff76`).

**Windows performs the SBX effects in a software APO.** The driver registers
`CtxRFX64.dll`, "Creative Render Audio Effects", on every render endpoint.
Static disassembly confirms a real-time floating-point module chain and an
input-to-output passthrough branch. Sound Blaster Command's OutFX master
controls five child effects through endpoint properties; it is not Direct
Mode and does not issue a global CA0132 bypass command. The evidence does not
yet prove that Windows never mirrors an individual setting into hardware.
Full trace, binary hashes and limits are in
[`WINDOWS_STACK_ARCHITECTURE.md`](WINDOWS_STACK_ARCHITECTURE.md).

**The GUI was rebuilding itself into unusability.** The mixer watch rebuilt
the whole window per ALSA event, including echoes of its own writes — one
rebuild per click, a stream of them per slider drag, and a rebuild racing
every route switch. Reported as the application hanging; it was never hung,
just replacing every widget under the pointer. Self-originated events are
now suppressed and external bursts coalesced.

**Stock PipeWire drives this card in S32LE.** Removing the project's
WirePlumber rule to get a "clean" baseline put the card into S32LE with MMAP
and 1024-frame periods, and handed volume back to the hardware. S32 is the
format tied to the original loud-buzz incident, so the default configuration
is the riskier one. Worth knowing before recommending anyone run without the
managed rule.

## Method notes worth keeping

**Measure with the right instrument.** Four comparisons failed before the
loopback worked: microphone against internal tap (different frequency
responses), music against music (the track moved on), a "recovery" that
never closed the PCM (comparing a state to itself), and THD near the noise
floor (measuring noise, which is why THD *rose* as level fell). The
loopback removed room, placement, transducer and microphone response at
once. It was Maks's idea.

**Check the instrument before believing the reading.** A 50% THD figure was
the line input clipping at −3 dBFS. A "second fault" was a `grep` matching
the `Items:` list instead of `Item0:`. Both would have become findings.

**Capture the fault, not the aftermath.** Every capture until the last was
taken after the fault cleared or after a recovery step had reset it. The
useful pair came from asking Maks to reproduce it and *not* fix it.

## Initial PCM-reopen isolation and fail-closed mitigation

Later waveform-qualified VFIO testing narrowed the repeatable trigger further.
On the exact guarded module, normal raw ALSA playback alternated between a
clean approximately 0.0007% THD state and approximately 26.407% THD after the
playback PCM was closed and reopened. OutFX remained off and no mixer control
needed to change.

The distorted waveform has discontinuities every 16 frames and strong even
harmonics. That is a useful implementation clue, but it does not yet identify
the faulty CA0132 request, stream-router field, or HDA transport operation.
The following candidates did not fix the reopen failure:

- HDA `snoop=1`;
- `position_fix=1` or `position_fix=2`;
- 1024/4096 period and buffer geometry;
- playback-first versus capture-first opening order;
- S32 playback;
- changing the normal ASI setup value from 4 to 7;
- replaying `ae5_post_dsp_stream_setup()` on every prepare;
- forcing the 2.0 speaker route.

One playback PCM held open continuously was decisive: opening and closing What
U Hear ten times stayed clean. The trigger is playback close/reopen, not
capture reopen.

The production mitigation has two independent layers:

1. `ca0132-ae5-disable-unsafe-outfx.patch` initializes AE-5 output effects
   off, rejects hardware OutFX enable with `-EOPNOTSUPP`, and does not replay a
   redundant off write.
2. The exact-card WirePlumber rule sets
   `session.suspend-timeout-seconds = 0`, keeping the managed S16 playback PCM
   open across application and idle transitions.

Two exact-module VM boots then held one playback PCM open. The first produced
ten clean What U Hear captures at 0.00073–0.00081% THD; a proper raw
OutFX-enable write was rejected with `EOPNOTSUPP`, three redundant off requests
did not disturb the stream, and subsequent captures remained clean. A full
guest shutdown/start with a new boot ID produced five more clean captures at
0.00064–0.00081% THD.

On the host, ten separate `pw-play` clients followed by ten seconds idle kept
the ALSA playback PCM `RUNNING` with an unchanged `trigger_time`. This verifies
the keepalive transport policy, but the AE-5 analog outputs are currently
unplugged, so it is not an analog listening result.

These guest starts include managed PCI reset and are **cold-like**, not a
motherboard power-removal cold boot. The Windows comparison is also currently
static rather than acoustic: disassembly confirms that Command OutFX controls
the `CtxRFX64.dll` software APO chain, while Linux's hardware OutFX control is
not equivalent. Runtime same-settings Windows capture still requires an
interactive Windows login and a usable comparison output or internal capture.

## PCM-reopen fix and qualification

Follow-up operation-level testing identified the corrupting lifecycle edge.
The generic CA0132 playback cleanup cleared the AE-5 HDA converter assignment
on every PCM close. Retaining that assignment made 12/12 immediate reopens
clean. A longer idle test then exposed a second edge: HDA runtime autosuspend
cleared the retained converter. Keeping only the HDA core cache caused silence
after resume, while globally disabling HDA power saving proved clean but was
too broad.

The final AE-5-only patch:

1. leaves the analog playback converter assigned when the PCM closes; and
2. holds a balanced codec runtime-PM reference until codec teardown.

The HDA controller DMA still stops and is released on close. Global
`snd_hda_intel power_save=10` remains enabled, the motherboard codec is not
held active, and system suspend retains the normal all-stream cleanup path.

The exact functional module completed:

- 8/8 clean captures after hardware OutFX enable was rejected;

- 50/50 final clean reopens with zero corrupt and zero silent results;
- 12/12 clean 48/96 kHz transitions; and
- 12/12 clean 2/6-channel transitions.

All measurements were bounded internal What U Hear captures. The AE-5 outputs
remained unplugged and the user's headphones remained on the motherboard

cold boot.

The patch is now the eighth entry in `kernel/series`. It passes strict

## In-place software EQ removes the double-volume failure

The virtual-sink Phase A design had a deeper problem than an unsafe handoff.
PipeWire applies cubic software volume at both the virtual sink and the
physical sink. Copying the physical 5% level to the virtual sink while leaving
the physical sink at 5% therefore compounded two stages; the effective scalar
could become approximately 0.25% before the cubic taper, explaining why the
processed path could appear silent or require an unexpectedly high displayed
volume.

PipeWire 1.6.8 exposes `audioconvert.filter-graph.N` directly on the existing
AE-5 node. An isolated null-sink probe logged successful runtime load and
removal of a builtin graph. The real AE-5 then accepted an identity graph
while suspended, muted, 5%, and physically unplugged. Both playback PCMs
remained closed and all prior state matched after unload.

Phase A now uses that direct API:

- the existing physical sink remains the default and remains the only
  volume/mute stage;
- activation verifies support and the exact target, requires OutFX off,
  suspends the sink, loads order zero, writes and verifies a per-node runtime
  signature, then resumes;
- unload performs the reverse operation and verifies marker removal;
- a PipeWire restart naturally drops the marker, so saved state is never
  mistaken for a live graph;
- the GTK page chooses and applies a profile in one action without a service
  restart.

Positive imported curves now receive deterministic automatic preamp. The code
models PipeWire's exact peaking-biquad coefficients, scans the combined
response at 44.1, 48, and 96 kHz, rounds attenuation upward, and adds 0.25 dB
margin. The imported `Windows My profile — Headphone` curve calculated
−10.80 dB.

The complete imported graph loaded on the real muted/unplugged AE-5 and
exposed the expected target/preamp/gain signature. Both playback PCMs stayed
closed. Unload removed the marker and state file; `wpctl`, raw ALSA controls,
and PCM status matched their pre-test snapshots. No audio was played on the
stock host kernel. The GUI-enabled gate passed 125 tests, strict Clippy,
release build, and formatting.

## Exact route and volume-preservation qualification

Live `EnumRoute` parsing of the revised ACP path exposed one exact
`sound-blaster-ae5-output-headphones` route at index 5 and no same-path
Speakers sibling. `ae5ctl route-status` initially rejected it only because
the Rust expectation still named the obsolete compound route. A manual
activation also revealed that PipeWire could restore an old saved route at
40% and unmuted over the current 5% muted state; no stream was open and every

The Rust setter now resolves route indices dynamically by exact `pw-dump`
name. For output routes it refuses an unreadable volume/mute state, mutes
before `set-route`, restores the prior software volume, and restores the
prior mute state last. Any error triggers a final mute attempt. The old
unconditional route block now permits changes only when the running release
is exactly `7.1.4-ae5-stable` and kernel taint is zero; all other kernels
remain fail-closed.
