# S32 track-transition investigation

Status on 2026-07-27: the fail-closed harness and trace tooling are implemented
and self-tested, but no exact-target AE-5 transition playback run has been
performed. The live managed sink remains the stable `S16LE` path. The user's
headphones are connected to the motherboard line-out, not an AE-5 output.

## Problem being isolated

A real music track change once produced a loud buzz under S32 playback. The
buzz survived desktop mute and stopped around PCM suspension. Earlier
sequential, zero-amplitude streams did not reproduce it. A useful trial must
therefore correlate the complete transition across four layers instead of
collecting only the final mixer state.

| Candidate | Authoritative evidence |
|---|---|
| Client or stream teardown | Timestamped client starts/exits, `pw-mon`, and the playback PCM open/close timeline |
| HDA DMA/link position | Kernel `hda_controller:azx_pcm_*` and `azx_get_position` tracepoints |
| PipeWire suspension | `pw-dump --monitor`, `pw-top`, WirePlumber/PipeWire journal, and before/after graph snapshots |
| Stale CA0132 DSP state | Mixer snapshots plus optional post-transition What U Hear RMS samples |

The upstream HDA controller already provides the required kernel tracepoints.
`azx_get_position` reports the selected DMA position and calculated delay;
the lifecycle events cover open, hardware parameters, prepare, trigger, and
close. See the upstream
[`controller_trace.h`](https://github.com/torvalds/linux/blob/v7.1/sound/hda/common/controller_trace.h)
and its call sites in
[`controller.c`](https://github.com/torvalds/linux/blob/v7.1/sound/hda/common/controller.c).
No new kernel patch is needed merely to observe these values.

## What the harness guarantees

[`scripts/track-transition-stress.sh`](../scripts/track-transition-stress.sh):

- resolves exactly one PCI `1102:0012`, subsystem `1102:0051` ALSA card;
- selects exactly one matching PipeWire sink and passes its node name to every
  `pw-play` client instead of using the desktop default;
- verifies `api.alsa.soft-mixer=true`;
- never enables S32 or edits WirePlumber configuration; `run s32le` refuses
  unless the already-live sink reports S32;
- requires at least five trials and an explicit `AE5_TRANSITION_ACK`;
- hard-mutes both `Master` and `Front`, checks them every 100 ms, and
  terminates while reapplying both mutes if either changes unexpectedly;
- uses only the bounded `-18 dBFS` fixtures generated by
  `audio-parity.sh generate-transitions`;
- limits the exact AE-5 sink to 20% for the run and leaves the sink, `Master`,
  and `Front` muted afterward;
- records complete close/reopen, abrupt disconnect, client format/rate
  replacement, a client-owned in-place format/rate renegotiation probe,
  overlapping gapless clients, and an idle/suspend-boundary transition.

The in-place case is not emulated with `pw-cli set-param`. A safe unlinked
probe demonstrated that the command accepts a write to a stream node's
write-only `Format` parameter, but it does not change the format advertised by
the owning `pw-play` client. The development-only
[`pipewire-format-renegotiate.c`](../tools/pipewire-format-renegotiate.c)
helper instead calls `pw_stream_update_params()` from the owning client, as
required by the
[PipeWire stream API](https://docs.pipewire.org/group__pw__stream.html). It
emits only digital silence and cycles one node through S16/S32 at 44.1, 48,
and 96 kHz.

Build the helper before a run (the harness also builds its default helper on
demand):

```sh
sudo dnf install pipewire-devel
bash scripts/build-transition-helper.sh
```

`--target 0` is a graph-only validation mode. On the current host, that mode
created zero links, exposed all four advertised format/rate states on one
stable node ID, and left both AE-5 playback PCMs closed. It did not alter the
live AE-5 sink, mixer, routing, or volume state.

That result proves that one owning client changes its advertised
`EnumFormat`; it does not prove linked renegotiation. Two guarded linked tests
used temporary PulseAudio-compatible null sinks, one fixed at S16/48 and one
at S32/96. Both negotiated the initial S16/44.1 stream, entered
`PW_STREAM_STATE_PAUSED` after the first S32/48 update, emitted no replacement
format callback, and were rejected by a bounded timeout. Each null sink was
unloaded afterward, the default sink stayed unchanged, and both AE-5 playback
PCMs remained closed. This may be a limitation of those fixed-format virtual
targets or an audio-stream/session-manager renegotiation gap; it is not
evidence that the exact AE-5 target works. Keep the linked case open until it
produces `complete updates=4 negotiated=5`.

The optional `AE5_TRANSITION_TAP_PROBE=front-muted` probe is deliberately
separate from the default two-switch invariant. What U Hear is downstream of
`Master`, so it cannot measure DSP output while `Master` is off. The probe
therefore waits for every playback PCM to close, mutes the exact PipeWire
sink, keeps `Front` hard-muted, enables `Master` only for a one-second capture,
and disables it immediately afterward. A level above the configured
`-25 dBFS` threshold creates an anomaly snapshot and aborts the run.

## Read-only preparation

This command discovers the real card, sink, format, policy, port, PCM state,
and planned transitions without changing anything:

```sh
bash scripts/track-transition-stress.sh --dry-run
```

The current host dry-run resolved ALSA card 0 and
`alsa_output.pci-0000_29_00.0.analog-stereo`, reported
`s16le 2ch 48000Hz`, confirmed software volume, and found both playback PCMs
closed. It also reported the existing 30% sink volume. No playback or state
write occurred.

## Full evidence run

Do not run this merely because the script exists. Keep the managed production
configuration on S16. A future S32 experiment must first have a deliberate,
reversible S32 test configuration and no AE-5 output connected to a listener.
The current headphones are connected to the motherboard line-out and nothing
is connected to an AE-5 output. That makes the unlinked graph validation
non-audible, but it does not substitute for the later attenuated electrical
capture required to qualify S32.

Tracefs is root-only on this host. In a separate terminal, capture the existing
HDA tracepoints while leaving the desktop PipeWire process under the normal
user:

```sh
sudo scripts/hda-position-trace.sh record 0 180 > hda-position.log
```

Then run the exact-target harness as the desktop user:

```sh
AE5_TRANSITION_ACK=hard-muted \
AE5_TRANSITION_TAP_PROBE=front-muted \
bash scripts/track-transition-stress.sh run s32le
```

The development account currently has no authenticated `sudo`, so the
HDA-position half of this procedure cannot be collected on the host yet.
Running only the rootless half can exercise client transitions, but it cannot
prove that the controller's DMA position remained correct.

## Reading a result

Treat any one of these as a failed trial:

- a client exit other than normal completion or the expected timeout;
- an in-place client log without all four completed format announcements;
- a playback PCM that does not close after its client exits;
- a PipeWire error count increase, XRUN, or node that does not reach the
  expected idle/suspended state;
- a non-monotonic or out-of-range `azx_get_position` sequence, an unexpected
  delay jump, or a trigger without the corresponding stop/close lifecycle;
- a What U Hear RMS above `-25 dBFS` after the clients have closed;
- a mixer fingerprint or route change not requested by the harness;
- either hardware mute leaving the off state outside the bounded tap probe.

S32 remains disabled after a clean run. Closing the release blocker requires
either a reproducible trigger with a root-cause fix or a repeated, physically
safe campaign showing that a specific fail-closed guard prevents the fault.
